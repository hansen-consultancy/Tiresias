---
id: I-101
title: Alerts carry facts about the machine to services outside it
stride: Information disclosure
likelihood: 2
impact: 3
status: mitigated
issue: 101
control: ASVS V14 Data Protection
---

**Threat.** Out-of-band alerts ([design](../alerts.md)) send events to ntfy, a webhook or a LcdHub
screen. Whoever can read the sink sees them: anyone who knows an ntfy topic on a public server, the
webhook's operator, someone standing at the LcdHub screen, or a program that created a pipe named
`LcdHub` before the hub did. A payload that held a secret name, a path, a program or a value would
tell them what this machine holds and where. A stolen sink credential (ntfy token, webhook header)
also lets its holder post fake alerts to you.

**Today.** Phases 2 to 4 send to a webhook, to ntfy and to LcdHub (`decoy.used` only). Every sink is public by default (event,
severity, count, time, a label you chose, a keyed hash of the subject), and each payload is built
from a record with no free-text field, pinned by a reflection test and a golden document. Only a
sink you mark trusted, saved with Windows Hello, gets names and paths, and no sink ever gets a
value, a token or a command line. The webhook URL and headers, and the ntfy topic and token, are sealed in `alerts.json` for Hello
and the recovery key; a file edited beside its seal or sealed without Hello is refused, and
widening needs Hello. Canary tests carry the decoy mapping through the planner and the webhook
and ntfy formatters into captured request bytes: no value or token canary appears, names only inside
a trusted webhook's `detail` and only the program's file name in a trusted ntfy body, the sink's
credential only in its header, never in the body, the URL or the log. The transport follows no
redirect, so the headers never reach another host. A webhook can sign each request the Standard
Webhooks way with a `whsec_` key sealed beside its header; only the HMAC leaves, and a canary test
pins that the key appears nowhere on the wire. A heartbeat carries the machine label and the time
only, on a trusted sink too. LcdHub gets the event's title and count only, on
a trusted sink too, never `detail` or the machine label; its canary runs through the link into the
bytes a fake hub received. The pipe is `CurrentUserOnly`, so a hub run by another user is refused; a
program running as you that serves `LcdHub` first learns those titles and counts, no more than the
screen shows anyone at the desk.

**Closes it.** Mitigated by phase 2. The residual is accepted: a public sink still learns that
something happened on a machine, and when; whoever holds a sink credential can post fake alerts, unless the receiver checks a webhook's
signature, whose key never leaves the machine.
A public ntfy server may hand a message to a phone platform's push service (Firebase, for the Play
Store app) to deliver it, and that service then sees what the topic does: one more reason a sink on
a shared server stays public.
