---
id: I-113
title: Secrets inside containers, WSL distributions and VMs are readable from the user's account
stride: Information disclosure
likelihood: 3
impact: 3
status: open
issue: 113
control: ASVS V13 Configuration
---

**Threat.** A program running as the user, without admin rights, reads secrets the user keeps in
environments meant to isolate work: every container's and image's environment through the Docker
engine pipe (open to `docker-users` and the installing user), the home folders of a running WSL
distribution through `\wsl.localhost`, a stopped distribution's `ext4.vhdx` copied from the
user's profile, and Hyper-V guests' disks and memory when the user is in Hyper-V Administrators,
which UAC does not filter. Devcontainer forwarding works the other way: code in a container asks
the host for git and registry credentials and SSH agent signatures. Tiresias seals none of these,
and consent never sees them.

**Today.** Nothing reports it. The design ([containers and VMs](../containers-and-vms.md)) adds a
doctor check that names what is reachable and how, by name only, with fixes that move the values
into the sealed environment and hand them over at run time (`tir env set`, `tir run`, `remoteEnv`
with `${localEnv:NAME}`, `WSLENV`). Looking inside an engine or distribution is opt-in, because the
Docker API returns values with names: the probe keeps names only and clears its buffers.

**Closes it.** Mitigated once phases 1 to 4 ship with the canary tests: the user is told, and has a
sealed path. The residual is accepted as part of [I-same-user](I-same-user.md): a value handed into
a running container is readable there while it runs. Devcontainers that ask Tiresias instead of
carrying values (the design's *Later*) would close most of it, and bring a threat entry of their own.
