---
id: E-91
title: A program running as the user uses the admin tier's SYSTEM service to gain privilege or undo protection
stride: Elevation of privilege
likelihood: 2
impact: 4
status: open
issue: 91
control: ASVS V8 Authorization
---

**Threat.** The optional admin tier ([admin-tier.md](../admin-tier.md)) runs a service as SYSTEM
and takes requests over a pipe any signed-in user can open. Malware running as the user tries to:
replace the service's binary; send a request that makes SYSTEM write, read or run something of its
choosing; thaw a frozen program or lift its network block; read the decoys back; act on another
user's processes; or create the pipe before the service does and pose as it to the app.

**Today.** Steps 1 and 2 are built: the service, its pipe, `status`, install, update and remove,
and the decoys held and listened for (`decoys.adopt`, `decoys.status`, `decoys.release`,
`events.wait`). What is built of each path:

- Built: the binary is copied to `%ProgramFiles%` and run from there, never from the per-user
  install folder. Its state folder, and `%ProgramData%\Tiresias` above it, are owned by
  Administrators with an ACL of SYSTEM and Administrators only; a folder a user made there first is
  moved aside, not used, and the service won't start while either isn't so.
- Built: the elevated copy from the per-user `admin\` folder follows nothing. A link anywhere in
  it, a file with another hard link, or one whose final path (read from its open handle) is
  outside the folder fails the install, so it can't carry a file only administrators can read into
  `%ProgramFiles%`, where users can read it. Each file is copied from the handle it was checked on.
- Built: a fixed list of typed actions, no paths to run and no generic file or registry access.
  `AdminCallerPolicy` refuses another protocol version, an unknown op, a service or another
  session's caller, an unelevated caller of an op that weakens protection, an op not built yet and
  any unexpected argument, before acting; tests pin each rule.
- Built: the caller is named from the client process's token, never from the request; a process
  created after the connection was accepted is refused, so a reused process id can't stand in.
- Built: the pipe is created first-instance-only, denies NETWORK, and lets users read and write but
  not create an instance; the next instance exists before a connected one is served.
- Built: the app and `tir` trust a reply only when the pipe's server process is the one the Service
  Control Manager runs as `TiresiasAdmin`, and connect at identification level.
- Built: every request is in the action log with its caller, never an argument; an op not on the
  list is logged as `unknown`.
- Built: every decoy action is keyed by the acting user's SID (the caller's, or for an elevated
  caller its session's user), and the service names files only after a SID of a user's form. One
  user can't see, adopt over or release another's set.
- Built: `decoys.adopt`'s set and file paths are checked by shape and size before anything is
  read (ports 1024 to 65535 and distinct, at most 16 places and 16 drive-rooted paths of at most
  1024 characters, no `..`, no control characters, no field more or less); the service writes only
  into its own state folder and never touches the files. `events.wait` takes at most 256 ids and
  waits at most 30 s. Refusals never quote a value; the action log has no argument.
- Built: at most 32 connections are served at once; past that, callers wait. Long polls held open
  by a program can't run the service out of handles, only make other callers wait.
- Built: SYSTEM never writes into a user's profile. The set goes back (`decoys.release`, removal
  of the tier) through an elevated process that creates `decoys.json` as a new file only, checks
  its final path on the open handle, and deletes it again if a link steered it elsewhere; the set
  then stays held (adopted again, or, with the service gone meanwhile, written back to its state
  folder for its next start). `decoys.release` needs elevation, so malware as the user can't read the decoys
  back; `decoys.status` gives kinds and a count, never a place, port or value.
- Designed, for the steps that add actions: reading the decoy files' attributes without following
  reparse points.

**Residual.** The install step itself runs from the per-user folder, elevated: a program that
replaced `Tiresias.exe` there gets elevated when the user approves the prompt. That is the same as
any per-user app that asks for elevation; the UAC prompt shows the publisher. Likewise the files it
copies come from the per-user `admin\` folder, which such a program could swap before the prompt.
A client that connects and exits at once leaves a window of microseconds, between its connection
and the service taking note of it, in which a process created then could take its id and pass.
An administrator elevated over a standard user's shoulder acts for that session's user: that is
by design (an administrator could do as much anyway), and an unelevated caller never acts for
anyone but itself. A user running the agent with the tier installed still has the decoy files'
contents, which is the point; which files are decoys, the ports and the values are not readable
by that user once held, though the doctor then can't skip decoy files by place either.
Whether a job freeze withstands `NtResumeProcess` from the user's own token is to be checked
before step 4.

**Closes it.** Built as designed, with tests for the caller rules, then a review of the service's
code by someone other than its author.
